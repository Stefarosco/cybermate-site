它解决的是哪种麻烦

「我这站安全吗？」

客户问这句话时，凭感觉答没用。这份报告每条都带证据原文，客户可以自己抽查。

「改完了，好了吗？」

每条都附一条可直接复制执行的验证命令，改完敲一遍就有答案。

「钱花在哪了？」

按「现在就要动手 / 可选加固 / 有空再修 / 可以忽略」分四节，先修哪条一目了然。

「怎么验证」那一列是这份报告最值钱的地方——它把「我觉得修好了」变成「我敲了一遍，有输出」。

三种交付形态

形态你给什么你拿到什么
A · 单站体检浏览器导出的 1 个 .harPDF 报告（本样例 18 页；站点越大页数越多）+ 一页行动清单
B · 多站／多环境3–5 个站，或生产 + 预发每站一份 + 一份汇总
C · 整改复检改完后重抓一次差异报告：哪几条消失了、哪几条还在

它明确不做的事

不做为什么
不下「存在漏洞」的结论缺一个响应头不等于能被攻破。报告只写「配置与最佳实践不符 + 证据」。
不主动发请求、不扫描只读你给的那个文件。不给文件，它什么都不做。
不猜证据拿不到原文就不报，宁可漏报。每条结论的证据都必须是输入里的原样子串。
不判断业务逻辑漏洞越权、支付逻辑、SQL 注入这些它完全不做。
不替代渗透测试这是「配置体检」，不是「攻击验证」。要后者得单独做。

交付流程

  1. 你导出 .har（浏览器 F12 → 网络 → 导出 HAR）
  2. 我跑报告、转 PDF，遮掉所有 Cookie 与凭据的值（名字与属性保留，不影响任何结论）
  3. 邮件正文只写最该先改的 3 条——其余在附件里
  4. 你改完重抓一次，我出差异报告：还差几条

这份工具自己靠什么可信

  • 2366 条自动化测试（开发层面的护栏，不是对你的抓包逐项检查）
  • 25 份真实站点抓包做回归；连同 ZAP 与构造样本，全部语料共 128 份
  • 34 条规则，每条都有参考依据（RFC / MDN / OWASP）
  • 1.7.1 版本号（规则集 2026.15）——每份报告的出处行都能对回具体版本与构建提交
  • 三条独立审查线（黑盒 / 真实样本 / 红队）各自签字，结项文档写清每轮覆盖到哪个提交

红队那条线一共拦下 6 次错误，其中 5 次拦的是「看起来全绿但其实没验到」——这段写在项目的复盘里，也是这份报告敢给人复核的原因。
